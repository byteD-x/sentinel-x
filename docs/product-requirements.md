# 产品需求：Sentinel-X AI 事故指挥中心

## 1. 文档状态

- 状态：开发前基线
- 产品阶段：MVP 规划
- 使用环境：本地隔离演练环境
- 重要声明：本文描述预期能力，不表示功能已经实现或指标已经达到。

## 2. 一句话定义

Sentinel-X 是一个面向故障演练的 AI 事故调查与受控恢复平台：它自动整理跨系统证据、给出可解释的根因假设和修复计划，由人批准后通过受限执行器恢复服务，并把全过程变成可回放、可评测的记录。

## 3. 用户与核心任务

| 用户 | 需要完成的任务 | Sentinel-X 提供的价值 |
| --- | --- | --- |
| 值班工程师 | 快速判断哪里坏了、为什么坏、下一步做什么 | 聚合证据、排序根因、生成受控方案 |
| 事故指挥者 | 了解进展、风险和责任边界 | 统一状态、时间线、审批与恢复判定 |
| 平台/安全工程师 | 限制 AI 权限并证明每次动作合规 | 白名单、最小权限、审批绑定、审计 |
| 面试官/评审者 | 判断候选人是否真正理解 Agent 工程化 | 可复现演练、故障 ground truth、量化报告 |

MVP 不面向真实生产用户，不承担生产事故处置责任。

## 4. 要解决的问题

传统事故处置的困难不只是“看不懂日志”，而是证据分散、调查过程易丢失、结论缺乏出处、恢复动作风险高，以及事后难以复现。普通聊天机器人只能给建议，无法可靠处理长时间等待、重试、审批、幂等和恢复验证。

本项目要证明：AI 可以参与事故调查，但必须被确定性工作流、安全策略和人工责任边界包围。

## 5. 核心体验

1. 场景操作员选择一个固定故障并启动演练。
2. 业务 SLO 恶化，告警入口创建并去重 Incident。
3. 系统自动查询指标、日志、Trace 和 Kubernetes 只读状态。
4. 调查器展示根因假设、置信度、支持/反对证据和调查预算。
5. 系统生成结构化 Remediation Plan，并明确风险等级与影响范围。
6. 审批者看到“将对哪个对象做什么、为什么、如何回滚”，然后批准或拒绝。
7. Action Gateway 二次校验后幂等执行已登记 Runbook。
8. 系统使用修复前后的 SLO 窗口判断恢复，生成事故回放和评测结果。

## 6. MVP 范围

### 6.1 演练业务

- `order-api` 调用 `inventory-api` 和 `payment-api`。
- PostgreSQL 保存订单，Redis 保存缓存或幂等键。
- 稳定负载持续制造订单流量。
- 三个服务输出可关联的 logs、metrics 和 traces。

### 6.2 首批故障目录

| 故障 | 预期主要根因 | 允许的 MVP 恢复路径 |
| --- | --- | --- |
| Pod 崩溃 | 指定 Pod 被一次性终止 | 观察 Kubernetes 自动拉起并直接验证，不执行多余动作 |
| 下游延迟 | 稳定流量阶跃导致 payment 容量饱和 | 审批后限定扩容，并在负载仍持续时验证 |
| 下游 5xx | inventory 进程内锁存错误状态 | 审批后滚动重启，验证新进程不再返回错误 |
| Redis 超时 | 缓存依赖超时 | 正确升级人工；Scenario Runner 独立清理，不计 AI 恢复 |
| 数据库锁 | 事务持锁阻塞请求 | 仅诊断和清理注入器，禁止 AI 操作数据库 |
| 错误版本发布 | 新版本导致错误率上升 | MVP 只诊断；版本回滚属于 R2，默认禁用 |

每个场景必须带版本化定义：注入方式、ground truth、预期证据、允许动作、恢复判定和清理方法。完整语义见 [故障场景目录](scenario-catalog.md)。Scenario Runner 的 cleanup 仅恢复测试夹具，不能记为 AI remediation。

### 6.3 功能需求

| ID | 优先级 | 需求 | MVP 验收证据 |
| --- | --- | --- | --- |
| FR-01 | P0 | 接收告警、去重并创建事故 | 同一告警指纹不会创建并行重复事故 |
| FR-02 | P0 | 持久化执行事故工作流 | Worker 重启后从原状态继续且不重复副作用 |
| FR-03 | P0 | 运行四类只读诊断工具 | PromQL、Loki、Tempo、K8s 查询均有参数和结果审计 |
| FR-04 | P0 | 生成可引用证据的根因假设 | 每个结论关联 Evidence ID，能区分支持和反对证据 |
| FR-05 | P0 | 生成结构化修复计划并风险分级 | 计划符合 Schema，未知动作被拒绝 |
| FR-06 | P0 | 对 R1 动作强制人工审批 | 无审批、过期审批或计划被修改时执行失败 |
| FR-07 | P0 | 幂等执行已登记 Runbook | 相同幂等键不会重复产生副作用 |
| FR-08 | P0 | 自动验证恢复结果 | 报告包含前后窗口、阈值和原始查询引用 |
| FR-09 | P1 | 展示实时事故时间线与回放 | 刷新页面后仍能重建关键事件顺序 |
| FR-10 | P1 | 运行固定数据集评测 | 产出机器可读 JSON 和人读 Markdown 报告 |
| FR-11 | P1 | 防御遥测提示注入 | 恶意日志不能改变权限、计划或工具边界 |

## 7. 非功能目标

以下均为目标，未有报告前不得表述为已达到：

| 目标 | 初始门槛 | 测量依据 |
| --- | --- | --- |
| 工作流可恢复 | Worker 重启后同一事故继续执行 | Workflow 重放与重启 E2E |
| 危险操作拦截 | 固定攻击集中拦截率 100% | 安全回归报告 |
| 重复副作用 | 固定故障集为 0 | ActionExecution 审计与场景状态 |
| 根因有效性 | 先建立无 AI 基线，再确定目标 | 版本化故障集的 Top-1 报告 |
| 可追溯性 | 每个诊断、审批和动作都有时间线事件 | 事故导出包完整性检查 |
| 本地可复现 | 新环境按文档可启动完整演练 | 干净环境演练记录 |

时间和成本指标的精确定义见 [测试与评测](testing-and-evaluation.md)，此处不重复口径。

## 8. 明确非目标

- 不连接真实生产集群，不宣称生产 SLA。
- 不做通用 AIOps、监控平台或工单平台。
- 不允许自主数据库修复、任意 Shell、动态 Runbook 或即时生成并执行脚本。
- 不做多云、多集群、多租户、计费和企业级 IAM。
- 不训练、微调模型，不开发推理引擎。
- MVP 不引入 LangGraph、Kafka、向量库、服务网格、eBPF 或图数据库。
- 不以“自动化率”作为唯一成功标准；正确升级给人工也是成功结果。

## 9. 产品验收

MVP 只有同时满足以下条件才算完成：

- 6 个场景都能从干净环境注入、观测、清理并重复运行。
- 至少一个场景完整通过“告警到恢复验证”，至少一个场景正确升级人工且不执行危险动作。
- 无审批、审批篡改、审批过期、重复请求和遥测提示注入均有失败测试。
- Worker 重启不会丢失事故或重复执行动作。
- 每次演练产出事故时间线、证据、决策、执行和评测报告。
- README、演示手册和实测报告只描述有证据支持的能力。

## 10. 待决策项

- 本地 Kubernetes 采用 k3d 还是 kind：以 Windows + Docker Desktop 的资源和稳定性基准决定。
- 模型 provider 与固定模型版本：以结构化输出可靠性、成本和可复现性决定。
- 本地身份方案：MVP 可使用明确标注 `local-only` 的预置身份，OIDC 延后。
- 首个根因 Top-1 目标：待无 AI 基线和首轮数据集运行后制定。
